# Application scaling transactions

`read_application_scale` and `application_scale_transaction` require a live, locally approved full-debug lease. They operate on Nickel's application compatibility policy and fixed GTK/Qt scale settings. They exclude output scaling, protected Remote AI Control preferences, arbitrary files and arbitrary commands. The remote backend is unavailable on Windows.

Read returns an observation generation, policy and at most two toolkit observations. `observation_started_at_us` and `observed_at_us` preserve the worker read interval relative to session start; owner delivery does not refresh either timestamp. `atomic: false` explicitly identifies sequential settings/toolkit reads. Snapshot delivery and transaction admission reject intervals older than one second from their start. A transaction supplies the exact generation and prior policy, plus `follow_nickel`, `unchanged`, or `custom` with `scale_120` from 60 through 480 in steps of 30. GTK custom scaling uses the integer buffer scale; Qt uses the fractional factor. Existing applications may require restarting. Per-toolkit results distinguish confirmed, unchanged, unavailable, failed, external conflict and uncertain; partial application is not all-or-nothing success. Policy persistence also controls future launch compatibility.

Local Settings and remote calls hold the same nonblocking, stable sibling-file transaction lock across read, journal intent, native mutation, completion and confirmation. Renaming the journal does not release that lock. Local persistence compares bounded prior bytes; remote persistence uses fresh owner revision checks. A competing Nickel transaction is rejected as busy. Uncooperative external writers do not honor this advisory lock, so fresh file/value checks also reject observed conflicts.

Before any setter, the admitted worker stages and synchronizes a durable ownership intent. The owner checks authority immediately before rename; the worker then synchronizes the containing directory and relevant ancestor directories before requesting native mutation. Failure leaves the operation uncertain and starts no setter. The first owned prior value survives repeated custom writes. Follow-Nickel restores it only while the current external value still matches Nickel's confirmed value. Qt observes the owned key directly: an absent override remains absent after reset, preserving inheritance.

Qt and the GTK keyfile backend replace only the fixed scale key, preserving unrelated lines. Preparation compares the target key against the original engine observation before adopting a file snapshot; final acceptance also compares the complete original bytes. The dconf path checks the original value again after connection preparation. Duplicate target groups/keys and unsupported immutable flags are rejected. Their actual native mutation boundary is the owner-authorized, fresh-CAS rename; directory synchronization completes on the worker. GTK's dconf backend prepares the fixed `ca.desrt.dconf.Writer.Change` message on a dedicated connection, then sends through the shared guarded transport with a fresh authority check before each native nonblocking socket write. The bounded attempt retires its dedicated connection on rejection or partial delivery; no remainder is resumed later. Mutation subprocesses are not used.

Dconf completion requires a matching successful method reply from the current bus owner, followed by fresh value observation. The upstream handler commits the changes before returning success. The fixed changeset encoding follows GNOME's implementation; this is a version-sensitive internal protocol, not an arbitrary D-Bus API. Sources: [dconf Writer interface](https://raw.githubusercontent.com/GNOME/dconf/master/service/ca.desrt.dconf.xml), [changeset encoding](https://raw.githubusercontent.com/GNOME/dconf/master/common/dconf-changeset.c), [writer commit and reply ordering](https://raw.githubusercontent.com/GNOME/dconf/master/service/dconf-writer.c).

Definitely unsubmitted failures (including failed preparation or the read immediately before submission) clear their intent only while the original authority still permits journal persistence. Revocation prevents that cleanup. A response timeout, partial send, or accepted write with uncertain completion retains its intent.

A durable pending intent separately records terminal native completion evidence. Matching an observed value alone never clears an unknown operation: a delayed accepted service request might still execute. Unknown intents remain uncertain without automatic retries, rollback or remote force-clear. A later authorized transaction can reconcile a terminal intent when a fresh value matches it. An accepted native service request may complete after cancellation; no later mutation is started, and a cancelled call cannot claim confirmed success. Directory synchronization may finish an already accepted rename, but does not authorize another write.

The shared D-Bus transport limits incoming frames before body allocation (8 KiB for dconf), authentication to 4 KiB, cumulative frames/bytes, queue depth, and setup time. It admits filesystem Unix sockets with normal authentication and no descriptor negotiation; TCP, exec, autolaunch and abstract addresses are unavailable. Replies are bounded before string decoding, and owner verification shares the completion deadline. GTK read-only helpers have a 4 KiB output cap and 750 ms wait deadline; cancellation kills/reaps on the admitted worker.

Configuration reads reject final-component symlinks and nonregular files with nonblocking open and pre/post descriptor evidence. The files and staged payloads are bounded to 64 KiB. Ordinary filesystem I/O, synchronization and process creation remain subject to the operating system and storage device; size caps do not make regular-file disk I/O interruptible. Synchronization requests establish the filesystem's persistence contract, not a proof against faulty hardware or filesystems that do not honor it. Native GTK/Qt services lack an atomic external-value CAS, so a final fresh read cannot exclude every uncooperative edit between observation and accepted mutation.

Validation uses owned XDG homes and isolated X11/session buses with audible cues disabled. The initial native fixture exercised real GTK keyfile/Qt tools; followup validation exercised the actual GTK dconf service on a private bus and direct Qt config replacement. Coverage includes ordinary-lease denial, full-debug read/change, held local input denial, cross-process lock contention, stale generation denial, repeated custom scaling, original-value restore, external Qt conflict, invalid scale and revoked-lease denial. Focused tests cover durable intents, terminal-evidence reconciliation, direct rename authority, unrelated-key preservation, bounded frames and helper cancellation. This does not establish native Windows support or DRM output behavior.

Final Linux evidence: 10 core DPI tests from the consolidated implementation, 20 toolkit tests, four observation/receipt tests, strict all-target Clippy for affected application crates, and the isolated private-dconf native fixture passed. The final native fixture delayed the actual GTK read by 150 ms and verified that the non-atomic worker interval includes that delay. Deterministic tests also verify stale owner delivery denial, original-prior conflict after the engine read, rejected-operation recovery, revocation-denied cleanup, and lost-receipt uncertainty. The shared transport additionally passed 14 framing/authentication/descriptor/timeout/per-write-authority socket tests and platform Clippy. Native fixture processes and control credentials were cleaned; copied binaries and validation logs were preserved outside the repository.
