# Spec 0231 settings and diagnostic-action implementation inventory

Source audit of `/projects/nickel`, 2026-09-10. This inventory was derived without builds or production edits. This is an implementation checklist, not a completion claim. Spec 0231 explicitly requires typed read/change of nonprotected settings and safe production-owned diagnostic actions; appearance and shell behavior alone do not satisfy that requirement. UI interaction is not a substitute for a typed transaction contract, particularly where the Settings application contains protected controls.

## Existing MCP scope

- `shell_behavior_transaction`: bar display scope, bar window scope, configured desktop count. `diagnostic_snapshot.shell_behavior` reads the domain. Production paths: `state.rs::commit_shell_behavior_transaction` / `remote_diagnostics.rs::remote_shell_behavior_transaction`; `remote_settings.rs::PreparedShellBehavior` stages `ShellSettings`. The appearance patch adds a final cancellation/emergency/deadline recheck to the existing rename boundary.
- Integrated appearance transactions: theme, accent hue/intensity, reduced transparency preference, animation preference; typed `read_appearance`/`appearance_transaction`; same shell-settings authority. It does not include wallpaper, file icon choices, OS-wide color-scheme publication, or all remaining settings.
- `diagnostic_action` has `Repaint`, `RefreshScene`, `StartFrameTrace`, `StopFrameTrace`, and exact-output `IdentifyOutput` (`nickel-remote-control/src/diagnostics.rs`). `diagnostic_snapshot` creates a bounded response, not an arbitrary file export. No typed platform re-query action is present in that enum.

## Explicit protected exclusions

`remote-ai-control.toml` and all listener/lease/pairing/audible-indication/Stop controls; update trust and arbitrary update installation/restart policy; `MaintenanceAction::SetPermission`, secure-storage recovery/secrets, credentials and identity; lock/security policy; arbitrary shell execution/source-tree/build/debug access; destructive storage policy; trusted indicator and emergency customization. These must be excluded field-by-field, not by making every page containing any protected field inaccessible to typed safe settings.

`MaintenanceService::inspect` mixes update/protection/permission/secure-storage status. A bounded diagnostic projection may include coarse capability/health where allowed, but must not forward its entire rich snapshot or all `MaintenanceAction` variants. `CheckForUpdates` is a possible benign owned re-query, not permission to install updates/change trust or invoke recovery.

## Recommended next self-contained domain

**Application scaling/toolkit compatibility** offers the highest direct debugging value after shell appearance: it addresses the project's live DPI/font-resizing work and already has typed policy, owned previous/applied values, bounded config loading, backend capability reporting, and verification-aware reset operations. Scope the implementation to the complete existing domain, including actual GTK/Qt writes/reset and truthful partial/restart outcomes—not just persisting a launch-environment flag. Start by extracting preparation/commit from `SettingsApp::apply_application_scale_policy` so both local Settings and MCP use one production transaction owner. The key missing contract is cancellation-safe external toolkit write ownership; audit `ToolkitScaleBackend::write` before exposing it.

A smaller follow-on with fewer external side effects is terminal **presentation** preferences (font/color/cursor/scrollback), but that is only part of the terminal domain; executable/directory settings remain explicitly outstanding. Display-layout transactions are high priority but less self-contained because safe rollback currently lives in the Settings UI, requiring movement into native owner policy first.

## Required evidence for each implemented domain

1. Typed schema rejects unknown/protected fields and arbitrary executable/path payloads.
2. Read reports bounded configured/effective values, source, generation, timestamp, and unavailable/pending/partial state.
3. Fresh prior/generation and underlying external revision checks prevent overwriting local changes; ABA and stale worker replies tested.
4. Preparation is bounded/off-owner; final mutation checks full-debug lease, protected state, shared input, request lifetime, emergency epoch and expiry immediately at commit.
5. Delay the actual worker/backend and revoke/timeout/disconnect; release delay and prove no late mutation, no stuck admission/input, and no silently extended lease.
   Separately lose or delay the completion receipt after native acceptance: the
   result must remain uncertain, retaining any ownership intent. Only a proven
   pre-submission rejection may clear that intent while still authorized. Generic
   string-error conversion is not evidence that a setter was never submitted.
6. Confirm the real production result natively (file/read-back/runtime/visible surface as appropriate), including restoration and failure outcome. Unit tests alone do not prove platform writes or rendering.
7. Exercise supported Linux and Windows owners separately; unsupported backend remains explicit, never inferred complete from Linux or cross-compilation.
8. Metrics use fixed domain/method/outcome labels; no values, paths, app names, network secrets or typed payloads retained.
